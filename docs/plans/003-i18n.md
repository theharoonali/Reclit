# 003 — Internationalisation

**Status:** implemented
**Scope:** frontend

> A separate plan from [002](002-dashboard-shell.md), not a continuation of it:
> this adds a dependency, a rule every future feature must follow, and a
> cross-cutting constraint on how all UI is written. The shell work in 002 is a
> consumer of this, not the other way round.

## Goal

Every user-facing string in the dashboard is a message key resolved at render
time, so the app can be translated without touching a component. English is the
only locale shipped; the locale comes from a cookie, and no URL changes.

## Backend (Agent 1)

None. `apps/api` is not modified. API error messages are not translated — that
is a separate problem and is out of scope here.

## Frontend (Agent 2)

- **Dependency:** `next-intl@^4.13.7` in `apps/dashboard/package.json`.
- **Files:**

  | Path | New/changed | Owns |
  | --- | --- | --- |
  | `apps/dashboard/src/i18n/config.ts` | new | `locales`, `defaultLocale`, `LOCALE_COOKIE`, `isLocale` guard |
  | `apps/dashboard/src/i18n/request.ts` | new | `getRequestConfig` — reads the cookie, validates it, loads the message file |
  | `apps/dashboard/src/messages/en.json` | new | every user-facing string, namespaced by surface |
  | `apps/dashboard/next.config.ts` | changed | wrapped in `createNextIntlPlugin("./src/i18n/request.ts")`; also given a real `NextConfig` type |
  | `apps/dashboard/src/app/layout.tsx` | changed | `<html lang>` from `getLocale()`, `NextIntlClientProvider`, `generateMetadata` from messages |
  | `apps/dashboard/src/config/nav.ts` | changed | `label`/`title` become `labelKey`/`titleKey` |
  | `app-sidebar.tsx`, `app-header.tsx`, `(app)/page.tsx`, `dashboard-empty.tsx` | changed | literals replaced with `t(...)` |

- **States:** no new UI states. A missing key throws in development, which is the
  intended failure mode.

## Integration (Agent 3)

None.

## Decisions

- **`next-intl` without URL routing.** The locale comes from a cookie with a
  fallback to `defaultLocale`; there is no `[locale]` segment and no
  `middleware.ts`. Routed locales would mean moving every route under
  `app/[locale]/`, adding middleware, and rewriting every `Link href` and the
  sidebar's `usePathname()` active-state logic — a large structural change for a
  dashboard that sits behind a login and does not need per-language URLs.
- **`next-intl` rather than a hand-rolled dictionary.** Plurals, interpolation
  and date/number formatting are where hand-rolled i18n fails, and this is the
  layer every future feature builds on.
- **Nav config holds keys, not text.** `config/nav.ts` was the one place display
  copy had leaked into configuration; `labelKey`/`titleKey` closes that.
- **Namespaced by surface** (`nav`, `sidebar`, `header`, `dashboard`,
  `metadata`), not by component — components get renamed far more often than
  surfaces do.
- **Brand and identity strings stay literal.** `APP_NAME`, the workspace name
  and the placeholder user are data, not copy; a translator would not touch
  them.
- **Error boundaries are deliberately not translated.** `global-error.tsx`
  replaces the root layout, so no provider is mounted above it; and an error
  boundary that depends on app context can fail while rendering the failure.
- **English only, no language switcher.** No translations were invented. The
  second locale is a file plus one array entry whenever a real translation
  exists.

## Risks / open questions

- **The whole app is now dynamically rendered.** Reading a cookie in
  `i18n/request.ts` opts every route out of static prerendering: the build went
  from `○ (Static)` to `ƒ (Dynamic)` for `/`. That is inherent to cookie-based
  locale selection. If static per-locale pages matter later, that means moving
  to routed locales — the decision above, revisited.
- Nothing writes the `locale` cookie. Until a switcher or a login preference
  exists, `defaultLocale` is always used and the cookie path is untested in
  practice.
- `en.json` and the code can drift — a deleted key is only caught when the
  component renders. `next-intl` can generate a type declaration from the
  message file (`experimental.createMessagesDeclaration`); not enabled here.

---

## Outcome

- **Shipped:** all of the above. Verified against the served HTML that every
  visible string — nav labels, section titles, search and notification aria
  labels, the workspace label, the page heading, subtitle and empty state —
  resolves from `en.json`; that `<html lang="en">` comes from `getLocale()`; and
  that `<title>` is `Dashboard` from `metadata.title` (it was the hardcoded
  "App" before, which is what proves the server pipeline works).

- **Deviated:**
  - `next.config.ts` needed a real `NextConfig` type annotation. Passing the
    config through `withNextIntl()` surfaced a pre-existing latent error: with
    only a JSDoc `@type` comment, `devIndicators: false` widened to `boolean`
    and failed to typecheck. The JSDoc comment was replaced with
    `const config: NextConfig`.

- **Not done:**
  - No language switcher, and nothing sets the cookie.
  - No second locale.
  - No message-key type generation.
  - API/tRPC error messages are still English strings from the server.
  - Not visually verified — no screenshot was possible in this environment.

- **Docs updated:** `docs/rules/FRONTEND.md` gained an Internationalisation
  section and its file tree now lists `i18n/` and `messages/`; the root-layout
  rule changed from "fonts + `<Providers>`. Nothing else, ever." to allow
  `<html lang>` and the intl provider. `docs/routes/root.md` records the
  rendering change from static to dynamic and the message-file dependency.
